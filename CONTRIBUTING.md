# Contributing

Repository, coding standard, and branch model — implementation-plan.md §3 item 0.1. "Done when the repository builds from a clean clone."

## Stack

Laravel 11 / PHP 8.3+ / MySQL 8.4 (InnoDB) / PhpSpreadsheet / BCMath. See [docs/system-architecture.md](docs/system-architecture.md) §9 for the full, authoritative stack list — this file does not repeat it.

## Setting up a clone

```
composer install
cp .env.example .env
php artisan key:generate
# create the database named in .env (DB_DATABASE, default municipal_payroll)
php artisan migrate --seed
```

`php artisan migrate --seed` should run clean on an empty database — that is the item 0.2/0.3 gate. If it does not, that is a bug, not an environment problem to work around.

### A known environment issue on Windows + WSL-mounted repositories

If this repository lives under a `\\wsl.localhost\...` or `\\wsl$\...` UNC path and PHP is the Windows-native build (not WSL's own PHP), two symptoms show up and are environment bugs, not project bugs:

1. **`composer install` times out extracting large packages** (`laravel/framework`, `phpunit/phpunit`) — `unzip.exe` over the 9P network filesystem is slow enough to hit Composer's default 300s process timeout. Fix: `composer config --global process-timeout 1800`, or build `vendor/` on a local (non-UNC) path and copy it in — either is fine, the second is faster.
2. **`vendor/bin/phpunit` and `vendor/bin/pint` fail with "Cannot open bootstrap script" or similar**, even though the file plainly exists. Cause: `is_readable()` returns `false` for every file on this mount (confirmed — `file_exists()`/`is_file()`/`fopen()` all correctly return `true` on the same path), and both tools check `is_readable()` before opening a file. Fix: run these two tools from a local copy of the source tree (`app/`, `database/`, `tests/`, `routes/`, `config/`, `bootstrap/`, plus `composer.json`/`phpunit.xml`/`pint.json`/`.env`) — `vendor/` itself can be copied once and reused. `artisan` commands and `composer`'s own autoloading are unaffected; they use `require`/`file_exists`, not `is_readable()`.

Neither issue affects the actual deployment target (a normal Linux or Windows filesystem, per architecture §8) — they are specific to developing directly against a WSL UNC mount from Windows-native PHP.

## Coding standard

[Laravel Pint](https://laravelshift.com/pint) (`pint.json`, `laravel` preset — effectively PSR-12 plus Laravel's own conventions). Run before committing:

```
vendor/bin/pint          # fix
vendor/bin/pint --test   # check only, e.g. in CI
```

Beyond formatting: follow the conventions already in `database/migrations/` — every migration cites the data-model.md section and, where relevant, the business rule (BR-xx) it implements, and every cross-row constraint that MySQL cannot express as a `CHECK` says in a comment which service will enforce it and when. A migration or model that touches a documented rule and doesn't say which rule is a review comment waiting to happen.

## Branch model

Trunk-based: `main` is always deployable-to-staging, work happens on short-lived branches named `<type>/<short-description>` (`feat/`, `fix/`, `docs/`, `chore/` — see recent history for the pattern already in use), merged back via pull request. No long-lived `develop` or per-sprint branch; the eight-week calendar in [docs/pre-oral-demonstration-plan.md](docs/pre-oral-demonstration-plan.md) §6 is a sequencing plan, not a branching structure.

## Tests

PHPUnit (`phpunit.xml`). `tests/Fixtures/` holds committed `.xlsx` fixtures generated by `php artisan fixtures:generate` (`app/Console/Commands/GenerateTestFixtures.php`) — re-run that command and commit the result if a fixture needs to change; do not hand-edit the binary files.
